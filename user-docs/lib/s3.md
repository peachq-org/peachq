# Reading from S3

peachq reads objects in an S3 bucket in place: a `` `:s3://bucket/key `` path is a file to `read1`, `read0`,
`hcount`, `-21!`, `get` and `key`, the same as a path on disk. A kdb+ database written to S3 reads the way it reads
locally: `hcount` of a compressed column is its uncompressed size, `-21!` shows its compression, `get` of a `.d`
gives the column names, and `key` of a partition lists its files.

The `.s3` namespace holds the settings: credentials, region, endpoint and how bucket names go into URLs. Their names
are the environment variables AWS and KX already use, so a session started in an environment that has them set
needs no call at all. Settings are scoped by path prefix, so one session can read buckets on several services, each
with its own credentials.

Every function and parameter: [.s3 API](https://peachq.org/docs/api/s3.q.html).

## The s3:// path

```q
q)P:"s3://kxs-prd-cxt-twg-roinsightsdemo/kxinsights-marketplace-data/db/2020.01.01/trade/";
q)hcount `$":",P,"sym"
2955832
q)-21! `$":",P,"sym"
compressedLength  | 69520
uncompressedLength| 2955832
algorithm         | 2i
logicalBlockSize  | 17i
zipLevel          | 6i
q)get `$":",P,".d"
`sym`time`price`size`stop`cond`ex
q)key `$":",P
`.d`cond`ex`price`size`stop`sym`time
```

`s3a://` and `s3n://` are read the same way. The bucket is everything up to the first `/`, and the key is the rest.

| Reader | On an `s3://` object |
|---|---|
| `read1`, `read0` | the object's bytes or lines, including the `(file;offset;length)` forms |
| `hcount` | the object's size, or a compressed object's uncompressed size (ref/hcount.md) |
| `-21!` | a compressed object's compression statistics, the empty dict for one that is not compressed |
| `get` | the object's q value: a `.d`, a column file, compressed or not |
| `key` | the names one level under the path, as for a directory; the path itself for an object; `()` for nothing |
| `select from`, `.csv.read`, `.j.read` | the format the key's suffix names (`.csv`, `.json`, …), as for a file |

**A ranged read fetches only its range.** `` read1 (`:s3://b/k;o;n) `` sends one GET with a `Range:` header, and a
ranged read of a compressed object fetches just the blocks it spans and the trailer. Parquet is different: a
`.parquet` key is read by DuckDB, which reads its own ranges, and so are `gs://`, `gcs://`, `r2://`, `hf://` and
`az://` paths.

**S3 is read-only here.** Writing a binary file to `s3://` with `set` or `1:` signals `'nyi`. Text and parquet
writes go through DuckDB as before.

`select from` a splayed table on S3 is not supported yet.

## Settings

| Key | Meaning |
|---|---|
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | the key pair requests are signed with (AWS Signature Version 4) |
| `AWS_SESSION_TOKEN` | a temporary credential's token, sent and signed with the pair |
| `AWS_REGION` | the region to sign for and to address, `us-east-1` when unset |
| `AWS_PROFILE` | the section of the shared files to read, `default` when unset |
| `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE` | the shared files, `~/.aws/credentials` and `~/.aws/config` when unset |
| `KX_S3_ENDPOINT` | another S3 service's URL, such as `http://127.0.0.1:9000` for a local MinIO; `https://` when it has no scheme. The bucket then goes in the path |
| `KX_S3_USE_PATH_REQUEST_STYLE` | `"1"` puts the bucket in the path (`host/bucket/key`) rather than the host name |

**No credentials means anonymous requests**, so a public bucket needs no settings at all.

**Where settings come from.** `.s3.getAutoConfig[]` reads them in this order, and the first place to have a setting
wins:

1. the environment variable of the same name (`AWS_REGION` falls back to `AWS_DEFAULT_REGION`);
2. the profile's section of the credentials file (`[default]`, or `[prod]` for `AWS_PROFILE=prod`);
3. the profile's section of the config file (`[default]`, or `[profile prod]`).

The files' `region` is `AWS_REGION`, and their `endpoint_url` is `KX_S3_ENDPOINT`. The key id, the secret and the
token come together from the first place that has a key id. A secret in the environment without a key id there is
not paired with a key id from a file. A setting found nowhere is missing from the dict.

## Configs and scopes

A config is one dict of the settings above. Each config serves a **scope**: the paths that start with a prefix
such as `"s3://flatfiles"`. The scope `"s3://"` is the **default**, which serves every path that no other scope
covers.

`.s3.config[scope;cfg]` sets the config for a scope:

| Argument | Meaning |
|---|---|
| `scope` | a path prefix, as a string or a symbol, or a list of them sharing one config. `::` is the default, `"s3://"` |
| `cfg` | a dict keyed as above, each value a string or a symbol; `::` for `.s3.getAutoConfig[]`; `()` to drop the scope |

**The default holds without a call.** It is `.s3.config[::;::]`, resolved at the first `s3://` read (or the first
`.s3.which` or `.s3.configs[]`, or when DuckDB's main database opens), so it picks up the environment as it is
then. Calling `.s3.config[::;cfg]` replaces it. Setting a narrower scope leaves the default alone.

**The longest scope wins, on whole path components.** A path is read with the config of the longest scope that is
a prefix of it up to a `/`, else with the default's. `"s3://flat"` covers `s3://flat/x` but not
`s3://flatfiles/x`. A trailing `/` on a scope makes no difference.

**A config is complete in itself.** A scoped config never takes a setting from the default. A scoped config with
no `AWS_REGION` signs for `us-east-1`, whatever region the default names.

Two services in one session, with no reconfiguring between reads:

```q
q).s3.config[::;enlist[`AWS_REGION]!enlist "eu-west-1"]
AWS_REGION| "eu-west-1"
q)`AWS_PROFILE setenv "massive"
q).s3.config["s3://flatfiles";::];     / its key pair, region and endpoint_url from ~/.aws
q)`AWS_PROFILE setenv ""
q)hcount `:s3://kxs-prd-cxt-twg-roinsightsdemo/kxinsights-marketplace-data/db/2020.01.01/trade/sym
2955832
q)hcount `:s3://flatfiles/us_stocks_sip/day_aggs_v1/2026/11/2026-11-13.csv.gz
322969
q).s3.which `:s3://flatfiles/us_stocks_sip/x
AWS_ACCESS_KEY_ID    | "AKIA..."
AWS_SECRET_ACCESS_KEY| "***"
AWS_REGION           | "us-east-1"
AWS_PROFILE          | "massive"
KX_S3_ENDPOINT       | "https://files.massive.com"
q).s3.configs[]
scope            AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN AWS_REGION  ..
---------------------------------------------------------------------------------------..
"s3://"          ""                ""                    ""                "eu-west-1" ..
"s3://flatfiles" "AKIA..."         "***"                 ""                "us-east-1" ..
q).s3.config["s3://flatfiles";()]
```

`.s3.which path` answers the config a path is read with, and the empty dict when no scope covers it.
`.s3.configs[]` is a table with a row per scope: the scope, then a column per setting, `""` where the config has
none. A list of scopes in one call gives one config several scopes, and one row each.

**DuckDB agrees.** Each config is also a DuckDB secret (`pq_s3_0`, `pq_s3_1`, ...) with the same scope, so
`.parquet` keys and SQL over `s3://` read with the same credentials as `read1`. DuckDB matches a scope as a plain
prefix, so each goes over with a trailing `/` to match whole components. The one difference that leaves: a scope
that names a single object (`"s3://b/t.parquet"`) covers that object for `read1`, but not for DuckDB, which reads it
with the next shorter scope. The default goes over as DuckDB's own default scope (`s3://`, `s3n://`, `s3a://`). The
secrets are made when DuckDB's main database opens, and kept in step after it. When two DuckDB secrets have scopes
of the same length, DuckDB takes the one whose name sorts first, so a secret of your own with no scope named before
`pq_s3_` wins over the default.

**The secret stays out of q.** The configs are kept inside the process, not in a q variable, because any client
connected over IPC can read a q variable. `.s3.config`, `.s3.which` and `.s3.configs` list the settings in
`.s3.getAutoConfig`'s key order and show the secret and the session token as `"***"`. The statements that make
the DuckDB secrets are not logged in `.duckdb.sqllog`.

**`.s3.getAutoConfig[]` returns the secret as it is.** It is an explicit call for what your environment resolves
to. Do not assign its result to a global in a process that serves clients. Under `-u` (restricted mode),
`.s3.config`, `.s3.which`, `.s3.configs` and every `s3://` read signal `'access`.

## Errors

| Signal | When |
|---|---|
| `'access` | S3 answered 403, or restricted mode. The text names the object and S3's error code: `access. s3://b/k: SignatureDoesNotMatch` |
| `'io` | the object is not there (`io. s3://b/k: NoSuchKey`), or another error status |
| `'conn` | the endpoint could not be reached |

`hcount`, `-21!` and `key` size an object with a HEAD request, whose answer has no body, so their text carries the
status instead of S3's code: `io. s3://b/k: HTTP 404`. The text never includes a credential.

**Region.** With no region set, requests go to `us-east-1`. A bucket in another region answers with its own region,
and the request is sent again there, once. Set `AWS_REGION` to skip that extra request.
